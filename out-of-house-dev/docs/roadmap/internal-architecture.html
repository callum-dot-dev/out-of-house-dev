02 · the customisation philosophy
02 · How customisation stays automated

Tweaks live in data, not in code.

Every client gets bespoke output without us writing new code. The magic is that the customisation parameters are rows in the database, not new files in a repo.

The tweak loop

Where the tweak knobs live

Three rules of the tweak layer

  1. If a tweak takes a row update, do it that way. No exceptions for "small custom changes" — the next person will ask for "just one more".
  2. If a tweak takes a code change, charge for it. That's a build, not a customisation. It enters the orchestrator pipeline like any other request.
  3. Every tweak knob has a default. A new customer is productive on day zero with the platform defaults; tweaks are optional from there.

What this reveals

  • Supabase is universal. Every service writes to it. Losing it = losing the business.
  • Claude API is universal too. Every service uses LLMs for something. Anthropic outage = degraded service across the board (fallback to OpenAI helps but isn't equivalent for tool use).
  • Claude Code is build-only. Coaching and courses don't touch it; LogoVault doesn't either. That gives us a smaller blast radius if the worker fails.
  • Slack only matters for delivery services. Per-client channels are how clients reach the engineer. SaaS and coaching don't need them.
  • MCPs are still nascent for us. One we publish (LogoVault), several we consume occasionally (Higgsfield, Notion, Monday, Meta Ads). Mostly used as enrichments rather than load-bearing.

From "we have an inbox triage problem" → live agent on the client's stack.

Flagship service. Highest-touch initial scope; highest-automation delivery. This is the canonical pattern every other build service inherits from.

Delivery flow
The tweak. The customer's brief and stack appear in one place — applications + projects. The orchestrator pipeline reads the brief and the integration metadata and produces a totally different Claude Code prompt for every client. The code we wrote is constant; the output is bespoke because the input is.

05 · websites · delivery
05 · Websites & landing pages

Brief in the morning, live by the evening.

The most automated build line. A starter site has a single human touchpoint — the brief call — and ships before the call recording's been transcribed.

Same-day-site toolchain

Internal services in play

  • Build: Claude Code → starter site repo (Next.js + Tailwind) → Vercel deploy.
  • Assets: LogoVault MCP for logos, Higgsfield MCP for hero imagery and team photos.
  • Hosting: Vercel (preview) → IONOS (DNS) → live. Care plan keeps it on Vercel with us paying the bill.
  • Care: automation_runs writes "uptime check" rows; nightly cron pings the site, alerts if down.
One starter-site template repo (private) is the seed for every starter site. Claude Code clones, edits, deploys. The whole flow is < 90 minutes of senior-eng time per site — the rest is wall-clock waiting for build/deploy.

Tweak knobs unique to web app builds

  • projects.preview_url — Vercel deployment URL, auto-updated per PR.
  • projects.metadata.tenancy — 'single' or 'multi'. Multi-tenant triggers RLS-by-default code generation.
  • projects.metadata.auth_providers — array, e.g. ['email','google','passkey'].
  • projects.metadata.billing_model — 'subscription', 'metered', or 'one-off'. Drives Stripe wiring in the build prompt.
  • projects.metadata.ai_features — list of AI features to bake in (RAG, chat, suggest, etc.).

Internal services in play

  • Code: Claude Code headless worker on Render / Fly — long-running execution per slice.
  • Repo: private GitHub repo per client; we keep admin until client takes over post-handoff.
  • Hosting: Vercel for the front-end, Supabase for the back-end. Both transferable to client account at handoff.
  • Observability: Sentry (errors), Supabase logs, claude_runs (LLM cost per slice).
  • Comms: Slack channel per client, per-PR preview URLs auto-posted, weekly digest email via digest-weekly.
The tweak that does the most work. projects.metadata.ai_features — listing things like ['rag-over-docs','inbox-triage','recommendation-engine'] — gets joined to template fragments in the planner. Each named feature is a known prompt module we've already shipped before; the LLM stitches them into the project's plan.

07 · Custom internal software

The spreadsheet replacement business.

Same orchestrator pipeline. The difference is the discovery phase — we sit with operators on-site and use a structured workflow-mapping LLM session to produce the brief.

Discovery layer (the only stage that differs)

Internal services unique to this line

  • Workflow capture toolkit (planned Q3 2026): a Notion template + LLM session script. Senior eng captures workflows in Notion using a structured template; an edge function extracts the DAG into JSONB on the project record.
  • Retool / refine.dev as fallback: for very lightweight admin UIs, we use Retool with a generated config. For anything serious, we generate a custom React admin under /app/admin/* in the client's repo.
  • Slack escalation bot (planned): when an operator marks a workflow as "stuck", the bot writes a feature_request and pings the engineer.
Manual surfaces. The on-site audit (irreducible — we need eyes on the actual ops floor) and the architecture sign-off (the moment the client commits to the build). Everything after stage 04 is the same automated pipeline as AI automations.

08 · maintenance retainer · delivery
08 · Maintenance retainer

The flywheel. Every retainer is a request loop running indefinitely.

Once a client is live, this is the steady-state interface. Most of our recurring revenue. Almost zero net-new infrastructure — it reuses every system already on this map.

The retainer loop

Tweak knobs (these are the retainer "configuration")

  • subscriptions.plan — 'lite' / 'standard' / 'heavy' — drives senior-eng hours/month + response SLA.
  • projects.health_status — 'healthy' / 'degraded' / 'down' — auto-updated by uptime ping; drives Slack alert priority.
  • feature_requests.priority — client-set; surfaces in order in the dev board.
  • projects.metadata.on_call — boolean. Premium retainers get out-of-hours response.
  • profiles.notify_email / notify_in_app — per-user preference, no separate config to maintain.
The retainer is just the platform running on autopilot for one specific client. No new internal tools, no new templates. Tools we built for delivery become the daily interface for the relationship.

10 · saas ops · logovault
10 · SaaS operations (LogoVault as exemplar)

SaaS = product running itself, with us watching.

The most "set and forget" line. Once seeded, the only manual surfaces are DMCA takedowns and onboarding new brands above the AI tagger's confidence threshold.

LogoVault operational flow

Internal services in play

  • Inventory build: SimpleIcons (CC0) seed + Brandfetch on-demand fallback (cached) + user uploads with Claude vision tagging.
  • Search: Postgres tsvector index on logovault_brands.search_tsv — no Elasticsearch.
  • Delivery: Cloudflare CDN in front of Supabase Storage for assets.
  • Billing: Stripe Billing subscription per plan tier. api_usage meters per call; overages billed monthly.
  • Distribution: direct UI + REST API + an MCP server we publish so Claude Code / Cursor users can call LogoVault as a tool.
The customer tweak. A LogoVault user's "tweak" is uploading their own brand library, which gets indexed alongside the public catalogue. Per-API-key scope means their private logos stay private without us writing any access-control code beyond standard RLS on logovault_brands.

11 · lead engine · delivery
11 · Lead engine (sold + internal)

The same pipeline serves us and serves clients — partitioned by RLS.

We run our own ICP through the engine to feed our own pipeline. Clients run their own ICPs through the same engine. Same code, same cron, different rows.

Engine pipeline (clients + us, on the same rails)

Why one engine serves everyone

  • Every lead row has a client_id. RLS prevents one client from seeing another's leads — the same way we isolate projects.
  • Adapters (places, companies_house, reddit) read from lead_sources which is global. Adding a new source benefits every client.
  • Per-client ICP + voice are the only "code-shaped" knobs. Both are LLM prompts stored as text.
  • When a client wants something genuinely outside the engine (e.g. integrate their CRM), that's a paid AI-automation build on top of the engine, not a fork of it.
The tweak that makes us look bespoke. voice_prompt + lead_icps.prompt are 2–10 paragraphs of natural-language English. Per client, that's where the bespoke work lives. Our code reads those two paragraphs and produces wildly different outputs for every customer — without ever being modified.

12 · AISEO programme · delivery

Audit → schema → authority → measure → tune.

The most "engineer-as-craftsman" line. Foundations are automated; authority work needs human judgement (we draft with AI, decide with humans).

AISEO retainer pipeline

Internal services in play

  • Audit: aiseo-audit edge function (deterministic, no LLM cost on the audit itself).
  • Foundations build: the standard Claude Code orchestrator — schema + llms.txt + page architecture changes are just normal build slices.
  • Monthly ranking pull: aiseo-ranker (planned Q3 2026) — hits each of the 6 LLM engines via their respective APIs, captures presence/rank/citation.
  • Authority drafting: Opus generates the long-form article in our voice; senior eng edits before publication.
  • Adversarial defence: cron scans competitor sites for indirect prompt-injection attempts; alerts to client Slack.
The red box. Outreach for citation placement (stage 3 of the authority row). LLMs can draft the pitch; humans own the relationship. We won't automate the "hey, would you link to this" outreach because relationship-based placements aren't credible when AI-sent.

What if a client wants something that's NOT a tweak knob?

It enters the standard build pipeline. The client posts a feature_request; claude-orchestrate scopes it; senior eng approves; build runs. Result: a new column, a new table, or a new edge function — committed to the platform and available to every client from then on.

This is how we compound. Every bespoke ask becomes a tweak knob the next client can use without a build. Year 1 the menu of knobs is short; year 3 it's the deepest in the market.

15 · adding a new service
15 · How a new service gets added to the platform

The standard playbook.

The platform's value is that adding service line #9, #10, #11 takes a week instead of a month. This is the checklist.

  1. Decide if it's a service, a SaaS, or a programme. Service = bespoke work using existing internal tools. SaaS = self-serve subscription. Programme = cohort-based teaching. Each has a different schema home.
  2. Write the marketing page first. A new entry in src/data/services.js (delivery service) or src/data/programmes.js (programme) or src/data/saasApps.js (SaaS). The site dropdown auto-updates.
  3. Identify the new tweak knobs. What columns / JSONB fields will the customer's customisation live in? Add them to the relevant tables in a fresh migration.
  4. Decide which existing edge functions can serve it. 90% of the time the answer is "claude-orchestrate plus the new tweak knobs". Resist writing a new edge function.
  5. Add a Stripe product. One product per pricing tier; metadata links back to the slug in the data file.
  6. Write the plan template. Add a row to plan_templates with phases + a Claude Code handoff brief.
  7. Wire Cal.com if there's a call. A sub-path on cal.com per service surface.
  8. Add the page-level analytics events. Drop into activity_events for in-platform; nothing third-party.
  9. Ship the marketing copy. Apply for AISEO inside the platform — same way clients do — to catch our own positioning.
  10. Add a row to this document. Update the master mapping table on page 03 + the per-service spread.

How much it costs us in variable spend to deliver one unit.

Knowing this is the difference between pricing for capacity and pricing for margin.

What this tells us

  • Senior eng time dominates every cost line. The platform isn't expensive to run; the engineer behind it is the cost.
  • SaaS is the only line where variable cost is near zero. That's why SaaS revenue is structurally different — every new sub is almost-pure margin once the product exists.
  • LLM cost is < 5% of total cost on every line. Provider price hikes are absorbable; engineer time hikes are not.
  • The way to scale is to drive senior-hours-per-unit down. Either by automating more (claude-orchestrate auto-merge) or by leveraging the dev bench (more engineers at a similar quality bar).
The point of the platform is to make each senior-eng hour produce more revenue than the year before. The map in this document is how we do it — every system reduces what a human has to do per customer outcome.
